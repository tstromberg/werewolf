## F-01: OCI hardlink traversal reads host files

- Severity: High.
- Confidence: High.
- Status: Remediated in the audited working tree.
- Regression: `unpack refuses a hardlink through an archive symlink`.
- Component: `cmd/howl/oci.zig`.
- Affected operation: OCI layer extraction by `howl _unpack`.
- At audit time, only the destination path was checked with `throughNoLink`.
- Symlink entries are permitted during extraction.
- Hardlink target paths were cleaned but not checked with `throughNoLink`.
- Hardlink lookup follows an earlier archive-created symlink.
- A crafted layer can target a readable file outside the extraction root.
- The target must be on a filesystem that permits the hardlink operation.
- The resulting image can contain the host file under an attacker-chosen name.
- This may expose build-host secrets through a built or published image.
- A harmless marker file reproduced the flaw on macOS.
- The outside marker and extracted file had the same inode.
- The extracted file contained the outside marker's contents.
- Linux Landlock likely blocks the demonstrated escape.
- macOS and FreeBSD do not receive that Landlock confinement.
- Validate every hardlink source beneath the extraction root.
- Resolve components with descriptor-relative, no-follow operations.
- Reject unsafe hardlinks if portable resolution cannot be guaranteed.
- Materializing a verified safe copy is another acceptable design.
- Add a regression archive containing a symlink-plus-hardlink sequence.

## F-02: OpenVAS can bypass its Fence network policy

- Severity: High.
- Confidence: High.
- Status: Explicitly measured and accepted for the Greenbone scanner.
- Regression: posture fails `network-fence-unbypassable` when either capability remains.
- Greenbone declares and tests the corresponding posture exception.
- Component: `forms/greenbone/form.yaml`.
- Related component: `cmd/fence/fence.zig`.
- OpenVAS receives `CAP_NET_ADMIN` and `CAP_NET_RAW`.
- OpenVAS also receives `netlink` and `packet` promises.
- Its connect policy permits destinations classified as `any`.
- Fence explicitly states these capabilities can bypass its rules.
- `CAP_NET_ADMIN` can alter networking and policy-routing state.
- `CAP_NET_RAW` enables raw and packet socket operations.
- A compromised scanner can exceed the form's claimed network boundary.
- Local-service access and lateral traffic become plausible.
- The form comment overstates isolation from PostgreSQL and gsad.
- Remove `CAP_NET_ADMIN` when scanning behavior permits it.
- Remove `CAP_NET_RAW` when scanning behavior permits it.
- Otherwise isolate privileged probing in a narrow broker.
- A dedicated scanner VM or network segment is a safer boundary.
- Document that Fence cannot enforce this policy against these capabilities.

## F-03: Root compromise can persist across bitten boots

- Severity: High.
- Confidence: High.
- Status: Open design limitation.
- Existing test: `check-secureboot` rejects a tampered signed UKI.
- Existing posture checks keep unsigned boot-chain gaps visible.
- Components: mount broker, updater, boot chain, and bitten installs.
- The mount broker accepts requests from any root process.
- Root can request access while the updater holds the victim device.
- The bitten kernel, stage zero, and GRUB are not authenticated.
- Secure Boot is currently outside the trusted boot design.
- Root can modify the mutable boot chain or trusted root-hash source.
- dm-verity cannot protect a mutable trust anchor.
- A root compromise can therefore survive an image replacement.
- Signed Unified Kernel Images should bind kernel and root hash.
- Secure Boot should authenticate the complete boot chain.
- Broker authorization should be narrowed where practical.
- Broker hardening alone cannot establish an immutable trust anchor.

## F-04: Execution is broader than declared binaries

- Severity: Medium.
- Confidence: High.
- Status: Partially remediated; per-service execution and production IPE gaps remain.
- Follow-up: IPE is now opt-in, enforcing the selected root globally.
- Its root policy still permits other native executables in that image.
- Signed prebuilt updates remain required before production rollout.
- A no-`exec` filter checks Leash's selected program descriptor number and
  exact flags; Landlock supplies executable identity.
- Regression: the seccomp test refuses other descriptors and extra flags.
- Components: Leash, Seal, dynamic loaders, and BusyBox.
- Leash initially opens and executes the declared program.
- At audit time, Seal permitted any `execveat` descriptor with `AT_EMPTY_PATH`.
- A permitted dynamic loader can execute another readable executable.
- `/usr` is executable and contains the verified image's programs.
- A BusyBox applet grant effectively exposes other BusyBox applets.
- Writable mounts remain mounted `noexec`.
- The verified read-only image limits attacker-supplied executable content.
- Claims of “only declared binaries” are therefore too strong.
- Describe the boundary as verified read-only binary execution.
- Treat syscall, filesystem, and network restrictions as the main controls.
- Enforce executable identity with IPE or an equivalent mechanism if required.

## F-05: Signed-release rollback remains possible

- Severity: Medium.
- Confidence: High.
- Status: Open design limitation.
- Existing posture: `boot-rollback-protected` fails without a TPM check.
- Existing secure-boot integration asserts that failure remains reported.
- Component: image update and boot selection.
- An older validly signed release can still be installed and booted.
- A compromised update path can restore a known-vulnerable release.
- Signature verification proves origin, not freshness.
- Store a monotonic minimum release version in protected state.
- Reject images older than that protected minimum.
- TPM NV storage is one possible implementation.
- Recovery procedures must preserve intentional rollback controls.

## F-06: Alpine verification retains SHA-1 compatibility

- Severity: Low.
- Confidence: Medium.
- Status: Hardened; no exploit was demonstrated.
- Legacy index signatures are denied by default.
- Only the explicit Alpine keyring opts into legacy SHA-1 signatures.
- Regression: a valid SHA-1 fixture fails without that opt-in.
- Component: `lib/apk.zig`.
- At audit time, every trusted key accepted legacy RSA/SHA-1 index signatures.
- Package control-member identity also uses a SHA-1 value from the index.
- Package payload data is separately checked with SHA-256.
- This appears inherited from Alpine package compatibility.
- Continued SHA-1 support increases cryptographic debt.
- Prefer SHA-256-only metadata and signatures when compatibility permits.
- Document the dependency if SHA-1 must remain enabled.
